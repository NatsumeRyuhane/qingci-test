## D-001：做客服坐席助手，而不是全自动回复
- 日期：2026-11-26 · 状态：已采纳 · 来源：项目启动
- 背景：题目要求“最大限度的回复自动化、精准、迭代”。在购买、退款或账号丢失这类问题上答错，代价很高。样本中的客服回复高度模板化（前 50 个模板覆盖 66%，见 [data.md](data.md)）。
- 决定：做一个坐席助手。它把每封咨询翻译并摘要成中文、进行分类、检索模板和相似案例，并起草一封措辞得体的日语回复，附带中文回译。按风险分流：只有少数低风险类别会自动发送，其余一律交给人工审核或升级处理。
- 影响：客服的修改是迭代优化的训练信号。随着离线评测证明某些类别足够安全，再逐步扩大自动发送的范围，以此提高自动化覆盖率。

## D-010：技术栈
- 日期：2026-11-26 · 状态：已采纳 · 来源：[#2](https://github.com/NatsumeRyuhane/qingci-test/issues/2)（正文与仓库所有者的评审评论）
- 编号说明：D-009（会话记录导出）记录在长期分支 `docs/agent-conversations` 上，测试结束时随 #9 合入，所以本文件在 `main` 上暂时从 D-008 跳到 D-010。
- 背景：其他所有 issue 都依赖技术栈的选择。约束：数据规模小（约 2.9 千个线程），每个案件的耗时主要在 LLM 调用上；样本数据不能进 CI（D-002）；贡献者使用的工具各不相同。
- 决定：
  - **后端：** Python 3.12 + FastAPI，对外只提供 REST API（`/v1`）。#3 的 Pydantic 契约直接用于请求校验和 OpenAPI 生成。排除 Rust（性能优势用不上，迭代慢）、Flask（校验和 OpenAPI 需要额外的库）、Django（ORM 模型与 Pydantic 契约重复，对这个规模过重）。
  - **前端：** React + TypeScript（Vite），作为独立服务只通过 REST API 与后端通信。这套 API 也是之后对外集成（#10、#11）的基础。排除 Jinja + HTMX（前后端耦合，复杂交互难做）。前端的 API 类型由后端 OpenAPI 生成，不手写。
  - **工具链：** 推荐 `uv` 和 `pnpm`，同时保留不依赖它们的备用路线：venv + pip 安装由 `uv.lock` 导出的 `requirements*.txt`；前端用 `npx pnpm@<固定版本>`。两条路线 CI 都会跑。lint 与格式化用 ruff 和 Biome，类型检查用 mypy 和 `tsc`，测试用 pytest 和 Vitest。
  - **LLM：** 不绑定服务商，支持任意 OpenAI 兼容端点。每个任务单独配置模型，可单独覆盖端点和 key。结构化输出一律用 Pydantic 校验并在失败时重试，不依赖 `json_schema` 模式，也不依赖 prompt caching。embedding 单独配置。用哪个模型由评测（#7）决定。
  - **检索与存储：** BM25（日语分词）+ embedding 的混合检索；向量在内存中暴力计算。MVP 用 SQLite（SQLAlchemy + Alembic），业务代码只依赖仓库接口和向量索引接口，为接口写共享测试。多实例部署、并发写入或语料超过约 10 万条时，新增 Postgres + pgvector 实现。
  - **测试：** CI 只用合成数据：fake LLM 的单元与契约测试，加上用真实 LLM 端点在合成数据上做结构性检查的 `llm-live` job。改动流水线行为的 PR 在 push 前用真实样本数据在本地运行，并在 PR 描述中报告汇总结果（见 AGENTS.md 第 7 节）。
  - **部署：** Docker Compose 加运维 TUI 脚本，放在 `deploy/` 下（#14）。
- 影响：#8 包含界面所需的 `/v1` 端点和一个统一的授权钩子；#10 在此基础上补齐对外集成的部分。`.env.example` 用 `LLM_*` 和 `EMBEDDING_*` 取代 `ANTHROPIC_API_KEY`。

## D-011：知识库记录“答案 + 何时适用”，所有条目带有效期
- 日期：2026-11-26 · 状态：已采纳 · 来源：[#5](https://github.com/NatsumeRyuhane/qingci-test/issues/5)（与仓库所有者的讨论），设计见 [提案 0003](proposals/0003-knowledge-base.md)
- 背景：#4 导入完成后发现，回复是否适用取决于时间（事故窗口、政策变化），而时间本身经常只能估计或没有；伪造的客服回复可能污染知识库（#18）；#6、中文客服和 #7 对知识库的需求各不相同。原先“模板集合、最新版本为准”的设想不够用。
- 决定：
  - **知识库记录运营方过去的答案，以及每种答案什么时候适用。** 不是 FAQ。使用方：#6（能检索、能填写的答案）、中文客服（中文说明）、#7（每封历史回复的标准答案和解决信号）。
  - **三个存储：** 邮件线程；稳定知识（模板、游戏事实、政策、日中术语表、意图目录，各自是独立的类型；风格指南是固定内容，不做版本和有效期，运营方告知措辞会变化时再考虑）；公告与事件（事故、维护、修复、政策变更）。模板以整段答复（`Message.core`）为单位，段落级推迟。
  - **每个条目都有有效期**，“稳定”指在被替换前一直有效。稳定知识按“现在”查询，公告与事件还要和案件的问题发生时间匹配。（`id`, `version`）是编辑历史，有效期是现实中的适用范围：每个条目以最新版本为准，由它的有效期决定在时间 T 是否适用，现实中的变化（例如政策变化）用取代旧条目的新条目表示。历史重放只看当时已经知道的版本（`known_from`），评测看不到当时还不存在的修正。
  - **出处与审核：** 每个条目记录来源邮件、来源方式（归纳或人工录入）和审核状态（`draft`/`approved`/`retired`/`needs_rereview`）。只有已批准的条目会提供给模型；未审核的条目只作为客服的参考，永远不自动发送。MVP 中由所有者审核模板和知识库，审核是信任的来源。所有者按覆盖率审核模板，直到覆盖 80%。
  - **意图是封闭列表**，每个模板属于一个意图。通用模板可以成为自动发送候选，门槛在案件上（意图在允许清单中、置信度高、无敏感标签且情绪不负面、第一封回复），并且永远不能胜过生效中的特定模板。
  - **时间带状态**（已知/估计/没有），没有就是没有，估计值标注区间。时间块追加在 LLM 请求末尾；限时模板只在生效时注入，窗口由代码检查。
  - **起草采用混合式 ReAct：** 安全相关的上下文由代码注入，模型可在约 4 步内调用只读工具，动作用 `complete_json` 校验，失败时回退到固定流水线。这把 #12 的一部分提前到 MVP。
  - **角色证据：** 假设输入中没有发件人元数据，角色只能从文本判断。导入步骤记录每封客服回复的证据（`Message.role_evidence`）。强证据只有引用佐证，以及与有佐证的回复正文相同；同一正文在多个线程中重复出现只是辅助证据，因为玩家可以把同一封伪造回复提交到多个线程。以没有强证据的回复结束的线程判为 `undetermined`，交给 #6。#5 只从有强证据的回复中学习；只有重复证据的正文作为带标记的草稿进入审核清单，所有者批准前不提供给模型。**投入生产前应向数据来源索取发件人元数据**（来自我们、玩家还是已知的邮件系统）；**没有元数据时，知识库不根据新的邮件线程自动更新**，否则伪造的回复可以持续污染知识库，系统不再可信。在“MVP 中所有者审核是信任根、生产中有元数据”这一前提下，剩余的伪造风险可以接受，MVP 阶段不再继续收紧文本证据的规则。
  - **存储：** 运行时 SQLite，行不可改写；审核通过每个模板一个 YAML 文件进行；由客户数据派生的内容不进 git，不含客户原文的人工内容（政策、意图、公告、公开术语）可以提交。
  - **`undetermined` 案件由 #6 的分析步骤判断**：#4 按设计是不调用 LLM 的确定性流水线，语义判断不属于它；#5 不修改案件状态。
  - **不回复也是一种答复：** 新增状态 `no_reply_needed`，由 #6 提议。“不回复”的标注只来自可解释的原因（重复提交、系统邮件），原因不明的线程不作为标准答案。重复提交且对应线程已回复时自动生效；只含系统邮件的线程只有在系统证据强、并且 #6 没有发现玩家的问题时才自动生效；其他情况转人工审核。
- 影响：#3 的契约需要扩展（后续 issue [#19](https://github.com/NatsumeRyuhane/qingci-test/issues/19)）；#5、#6、#7、#12 的范围按提案 0003 调整；#7 在 3 月内按日期切分，并按时间状态报告。

## D-012：评测数据在时间上均匀切分为 train / dev / test，知识库只用 train
- 日期：2026-11-27 · 状态：已采纳（取代 D-011 中“#7 在 3 月内按日期切分”一句） · 来源：[#5](https://github.com/NatsumeRyuhane/qingci-test/issues/5#issuecomment-7206340279)（与仓库所有者的讨论）、[#7](https://github.com/NatsumeRyuhane/qingci-test/issues/7)
- 背景：知识库（#5）要从历史回复中构建，评测（#7）也用同一批历史线程。如果评测集的线程进入知识库，评测数字会虚高，不再能反映系统的真实效果。D-011 原定在 3 月内按日期先后切分，但这样 train 只有前期的数据：知识库学不到“某个事件已经结束”这类只在后期出现的信号（例如修复之后的回复），评测集也只代表月底，不含两次集中的事故（3 月 2 日、3 月 15 日）。数据见 [data.md](data.md) 的“切分”。
- 决定：
  - **三侧：** train（70%）构建知识库；dev（15%）用于调参（阈值、LLM 评审校准、prompt 迭代）；test（15%）是评测集，只在报告基线时运行，不在上面调参，否则它会逐渐失去代表性。
  - **在时间上均匀分布的分层抽样：** 按线程顺序（线程 ID 即提交顺序，覆盖全部线程；问题发生时间是玩家填写的，有离群值，部分线程没有）每 100 个线程一层（约一天），层内按固定种子的哈希顺序分配。种子和参数写在代码中（`copilot/eval/split.py`），切分结果（含线程 ID）写在 `data/processed/split.json`，不提交。
  - **重复提交的线程整组放在同一侧**（组内最早的线程所在的层）。
  - **按时间先后切分作为对比**（`--method chronological`），衡量系统面对从未见过的时期（新事故）时的表现。
  - **均匀抽样的代价是“未来”的线程进入 train**：3 月 2 日的测试案件旁边有 3 月 3 日的训练线程。控制方法：
    - 知识库构建**只读 train 线程**，跨线程的角色证据也只在 train 线程内重新计算。可以测试的不变量：从输入中删掉 dev 和 test 的线程，知识库构建的结果不变。
    - #7 历史重放时，每个案件只看 `known_from` 不晚于它的“现在”的知识库版本（D-011），以及“现在”之前的线程。从历史数据归纳的条目，`known_from` 取来源回复时间的上界，误差只会让知识出现得更晚，不会更早。
  - **人也不看评测集：** 人工编写 `knowledge/`（意图目录、公告与事件、术语表）和审核模板时只看 train 的数据；审核清单只含 train 的模板；dev 和 test 只以汇总数字的形式出现在报告中。
  - **评测时知识库不加入 dev：** dev 和 test 的评测都用只由 train 构建的知识库。
  - **标准答案的切片：** #7 的主指标用有强角色证据的客服回复；只有“重复出现”或关键词证据的回复单独作为一个切片报告。只用强证据会让评测集偏向常见模板（强证据大多来自与其他回复正文相同），夸大 top-3 准确率。弱证据的回复不能用于学习（会污染知识库），但用于评测时，伪造的回复只会带来噪声。
- 影响：#5 的知识库构建以 `split.json` 为输入，切分与案件不一致时报错；#7 的切分任务改为使用 `copilot split`，并在历史重放中按 `known_from` 过滤；提案 0003 §14 已注明被本决策取代。

## D-013：模板覆盖率如实报告，不设 80% 的验收门槛
- 日期：2026-11-27 · 状态：已采纳（取代 D-011 中“所有者按覆盖率审核模板，直到覆盖 80%”） · 来源：[#5](https://github.com/NatsumeRyuhane/qingci-test/issues/5)（仓库所有者对模板候选结果的决定）
- 背景：D-011 和 #5 的验收标准要求模板覆盖至少 80% 的历史客服回复。按 D-012 只用 train、并按提案 0003 §11 只从角色证据充分的回复中学习后，候选的来源回复覆盖 train 全部客服回复的 77.9%（[data.md](data.md) 的“模板候选（train）”）。剩下的主要是只有弱证据的回复（19%），它们按设计不能学习：玩家可以写出客服的问候语。
- 决定：
  - **不为了达到数字而放宽规则。** 不降低角色证据的要求，不为了覆盖率调低近似去重的阈值，不把弱证据的回复算作学习来源。这些都会让伪造或不可靠的内容进入知识库，换来的只是更好看的数字。
  - **覆盖率按两种口径如实报告**：占 train 全部客服回复的比例（主口径），以及只算角色可信的回复（强证据和“重复出现”）的比例。
  - **80% 是有更多数据时追求的目标**（例如有发件人元数据、能信任更多回复时），不是 #5 的验收门槛。
  - **审核全部候选**：样本中只有 76 个候选，所有者按覆盖率顺序全部审核，而不是审核到某个覆盖率为止。
- 影响：#5 的验收标准相应修改；提案 0003 §4 和“如何判断它是否有效”已注明。提高覆盖率应当靠改进系统本身（例如更多可信的数据），而不是改变口径。

## D-014：knowledge/ 中的条目以 PR 评审作为所有者的审核
- 日期：2026-11-27 · 状态：已采纳 · 来源：[#5](https://github.com/NatsumeRyuhane/qingci-test/issues/5)
- 背景：只有已批准（`approved`）的知识库条目会提供给模型（D-011）。从数据中归纳的条目（模板）通过审核文件审核；人工编写、提交到 `knowledge/` 的条目（意图、政策、公告与事件、术语表）需要一个同样可靠的批准方式。提案 0003 §12 要求这些运营内容“像代码一样评审”。
- 决定：`knowledge/` 中的条目以 `review_status: approved` 提交，**PR 的评审就是所有者的审核**；未经评审的改动不能合并（AGENTS.md 第 5 节）。修改已合并的条目时新建版本，不改写。编写时只参考 train 的数据（D-012），提交前用 `copilot kb knowledge --check-leaks` 检查是否混入样本原文。
- 影响：意图目录和政策在合并后即可被 #6 使用；审核的记录就是 PR 的评审记录。规则写在 [knowledge/README.md](../knowledge/README.md)。
