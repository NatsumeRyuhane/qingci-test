# 样本数据概况

来源：`data/raw/脱敏数据2026.2.10.xlsx`（未提交，见 [data/README.md](../data/README.md)）。除特别注明外，以下数字都来自导入步骤（#4）的清洗结果，可用 `uv run copilot ingest --stats` 复现。清洗规则见 [`backend/copilot/ingest/`](../backend/copilot/ingest/)。

## 结构

一个工作表，5,950 行数据，三列：

| 列 | 含义 |
|---|---|
| `メールID` | 线程 ID（共 2,872 个） |
| `メールID枝番` | 线程内的邮件序号，1 到 12，线程内不重复 |
| `本文` | 邮件正文（纯文本，中位数约 410 字符，最长约 5,900 字符，5 封为空） |

线程长度分布：1 封：670 · 2 封：1,705 · 3 封：292 · 4 封：130 · 5 封及以上：75。
App 版本为 1.0.x 到 1.4。

## 邮件类型

表格中没有标明发送方的列，发送方由导入步骤按以下特征判断（`MessageRole`）：

| 发送方 | 邮件数 | 特征 |
|---|---|---|
| 客服（`agent`） | 2,759 | 去除引用后开头是 `いつもご利用いただきありがとうございます。『ぽちゃガチョ！』サポート担当です。`（2 封只有固定结语） |
| 玩家（`player`） | 3,033 | 2,619 封游戏内表单；109 封不是表单的第 1 封（直接发来的邮件、从其他渠道转来的咨询）；305 封后续邮件中的玩家追问 |
| 系统（`system`） | 133 | 退信和客服工具的批量回复报告。它们各自是只有一封邮件的线程，不是咨询 |
| 未知（`unknown`） | 25 | 正文为空（5 封），或去除引用后什么都不剩（20 封，例如纯转发） |

- 首轮探索时估计的“约 2,950 封客服回复”把玩家追问中**引用**的客服回复也算了进去；去除引用后是 2,759 封。同理，玩家追问实际约 300 封，而不是约 140 封。
- **第 1 封**的游戏内表单字段固定：

  ```
  アカウントID / プレイヤー名 / アプリバージョン / ご利用のOSバージョン / ご利用端末名 /
  お問い合わせ内容の種類 / ご利用環境 / 問題が発生した日時 / メールアドレス /
  お問い合わせ内容 / 添付ファイル
  ```

  很多字段为空，自由文本在 `お問い合わせ内容` 中。`添付ファイル` 在所有表单中都为空。
- 有 679 个线程没有客服回复（其中 670 个只有一封邮件）。

|---|---|---|

## 时间信息

表格没有时间列，能用的时间只有两种：

- **问题发生时间**（表单的 `問題が発生した日時`，玩家填写）：2,149 个线程有完整的日期和时间（2024-02：201 · 2024-03：1,942 · 2024-04：5 · 2024-09：1），468 个只有 `HH:MM`、没有日期，255 个没有表单。数据几乎全部集中在 2024 年 3 月。
- **发送时间**：只能从后续邮件的引用引导行中读出，精确到分钟。只有引导行能确定发送方（有客服发件人名称或其他发件人名称）、并且引用内容恰好与之前的一封邮件吻合时才采用，共恢复 258 封邮件的发送时间（`Message.sent_at`）。其余邮件的发送时间未知。

## 关键发现

1. **回复高度模板化。** 去掉引用内容和固定的问候语、结尾后（`Message.core`），2,759 封客服回复有 618 种不同的正文，**最常见的 50 种覆盖 71%，最常见的 100 种覆盖 79%**；另有 467 封是只出现一次的回复。这就是题目所说的“小型知识库”：核心工作是给咨询分类并检索出正确的模板，再由 LLM 调整措辞。
2. **部分模板只适用于某次事故。** 例如：3/2 11:00–14:00 的 App Store 故障导致购买异常；3/15 排名奖励出现“構成エラー”错误；以及一个“仍在调查中”的广告奖励问题。这些模板只在特定时间窗口内有效，不能用于无关的问题。
3. **回复遵循固定结构：** 问候 → 致歉（视情况）→ 答复 → “如果问题仍未解决，请再次联系我们” → `今後とも『ぽちゃガチョ！』をよろしくお願いいたします。` → `※本メール内容の無断掲載、無断複製、転送はお控えください。` 中文客服最容易在这类语体上出错，因此起草的回复应遵循这一结构。导入时把问候语和结尾拆到 `Message.greeting`、`Message.closing`；10 封客服回复没有结尾。
4. **引用的历史邮件很杂乱。** 共有 2,108 封邮件带有引用，按引用起点的格式：`>` 行 1,861 · Gmail 引导行（`2024年3月29日(金) 16:32 … <>:`，有时带 `午前/午後`）197 · `Original Message`/`____` 等分隔线 26 · 其他语言或折行的引导行 15 · iPhone 引导行（`2024/03/29 12:18、… のメール:`，有时后面不带 `>`）7 · `On … wrote:` 1 · Outlook 邮件头块 1。客服回复也会在结尾之后用 `>` 引用玩家的表单。约 15 封玩家邮件（约 0.5%）把之前的邮件不加任何引用标记地粘贴在正文里，规则无法安全地识别，这部分保留在 `body` 中。
5. **部分字符丢失。** `・`、`①②③` 和一些项目符号被替换成了半角 `?`。导入步骤修复了 1,020 封邮件中的常见情况：已知短语（如 `ご意見?ご要望`）449 处、行首的项目符号 2,303 处、汉字/片假名之间的分隔符 154 处、丢失的孤立字符 8 处。没有上下文的 `?` 保持原样，原文在 `Message.raw_body`。
6. **脱敏留下了空缺，但并不彻底。** 表单中的账号 ID、玩家名和邮箱地址都是空的，发件人地址显示为 `<>`。但自由文本中仍可能出现个人信息，例如从其他渠道转来的咨询中带有电话号码，所以引用样本时仍要遵守 [data/README.md](../data/README.md) 的规则。
