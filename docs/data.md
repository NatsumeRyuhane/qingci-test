# 样本数据概况

来源：`data/raw/脱敏数据2026.2.10.xlsx`（未提交，见 [data/README.md](../data/README.md)）。除特别注明外，以下数字都来自导入步骤（#4）的清洗结果，可用 `uv run copilot ingest --stats` 复现。清洗规则见 [`backend/copilot/ingest/`](../backend/copilot/ingest/)。

## 结构

一个工作表，5,950 行数据，三列：

| 列 | 含义 |
|---|---|
| `メールID` | 线程 ID（共 2,872 个） |
| `メールID枝番` | 线程内的邮件序号，1 到 12，线程内不重复 |
| `本文` | 邮件正文（纯文本，中位数约 410 字符，最长约 5,900 字符，5 封为空） |

线程长度分布：1 封：670 · 2 封：1,705 · 3 封：292 · 4 封：130 · 5 封及以上：75。
App 版本为 1.0.x 到 1.4。

## 邮件类型

表格中没有标明发送方的列，发送方由导入步骤按以下特征判断（`MessageRole`）：

| 发送方 | 邮件数 | 特征 |
|---|---|---|
| 客服（`agent`） | 2,759 | 去除引用后开头是 `いつもご利用いただきありがとうございます。『ぽちゃガチョ！』サポート担当です。`（2 封只有固定结语） |
| 玩家（`player`） | 3,033 | 2,619 封游戏内表单；109 封不是表单的第 1 封（直接发来的邮件、从其他渠道转来的咨询）；305 封后续邮件中的玩家追问 |
| 系统（`system`） | 133 | 退信和客服工具的批量回复报告。它们各自是只有一封邮件的线程，不是咨询 |
| 未知（`unknown`） | 25 | 正文为空（5 封），或去除引用后什么都不剩（20 封，例如纯转发） |

- 首轮探索时估计的“约 2,950 封客服回复”把玩家追问中**引用**的客服回复也算了进去；去除引用后是 2,759 封。同理，玩家追问实际约 300 封，而不是约 140 封。
- **第 1 封**的游戏内表单字段固定：

  ```
  アカウントID / プレイヤー名 / アプリバージョン / ご利用のOSバージョン / ご利用端末名 /
  お問い合わせ内容の種類 / ご利用環境 / 問題が発生した日時 / メールアドレス /
  お問い合わせ内容 / 添付ファイル
  ```

  很多字段为空，自由文本在 `お問い合わせ内容` 中。`添付ファイル` 在所有表单中都为空。
- 有 679 个线程没有客服回复（其中 670 个只有一封邮件）：132 个是系统邮件，5 个是空邮件，542 个是玩家咨询。这 542 个线程分布在整个时间段和线程 ID 范围内，不是数据截止造成的积压。按原因（[提案 0003](proposals/0003-knowledge-base.md) 设计时的一次性统计，比较规范化后的咨询内容）：
  - 308 个是**重复提交**：咨询内容、设备、App 版本和问题发生时间都与一个已回复的线程相同，两者的线程 ID 距离中位数为 1。运营方只回复了其中一个。
  - 68 个彼此重复，但没有一个得到回复；32 个内容太短（少于 20 个字符），无法比较；134 个没有重复，原因不明。

  按同一规则（[`ingest/duplicates.py`](../backend/copilot/ingest/duplicates.py)）分组，整个样本中有 380 组重复提交，共 773 个线程（包括得到回复的那一个）。同组线程的 ID 距离中位数为 1，p95 为 3。

## 角色证据

样本中没有发件人元数据，角色只能从文本判断。导入步骤为每封客服回复记录判断依据（`Message.role_evidence`，规则见 [提案 0003](proposals/0003-knowledge-base.md) §11）。按最强的一条依据：

| 依据 | 强度 | 客服回复数 |
|---|---|---|
| 引用佐证：之后的邮件用标明客服发件人的引导行引用了它 | 强 | 247 |
| 正文与另一封有引用佐证的客服回复相同（146 种正文） | 强 | 1,608 |
| 同一正文在至少 3 个线程中出现 | 辅助 | 448 |
| 只有固定的问候语或结语 | 弱 | 456 |

有强证据的共 1,855 封（67%）。线程的最后一封邮件不可能有自己的引用佐证（没有后续邮件引用它），所以以客服回复结束的线程能否判为已回复，取决于这封回复的正文是否与某封有佐证的回复相同。

## 案件状态（按线程的最后一封邮件）

| 最后一封 | 状态（`CaseStatus`） | 线程数 | 含义 |
|---|---|---|---|
| 有强证据的客服回复 | `replied` | 1,303 | 之后没有玩家追问，可以认为已结案 |
| 玩家邮件 | `open` | 567 | 玩家的咨询或追问还没有回复 |
| 系统邮件、无法判断发送方，或没有强证据的客服回复 | `undetermined` | 1,002 | 单看结构无法确定是否已结案，由 #6 的分析步骤判断 |

`undetermined` 中：

- 863 个以没有强证据的客服回复结束。玩家可以在正文开头写出客服的问候语，或把收到的回复粘贴回来，只凭关键词或重复出现不能让案件离开待处理队列。这些大多是真实的、只出现一次或很少出现的回复，由 #6 确认。
- 132 个只含一封系统邮件的线程、5 个只含一封空邮件的线程、1 个客服回复之后紧跟退信的线程（我们的回复可能没有送达），以及 1 个客服回复之后是两封无法判断发送方的邮件的线程。以系统邮件结束不能当作已结案：退信可能是我们的回复没有发出去，也可能是玩家粘贴的内容，或伪装成系统邮件的输入。

## 时间信息

表格没有时间列，能用的时间只有两种：

- **问题发生时间**（表单的 `問題が発生した日時`，玩家填写）：2,149 个线程有完整的日期和时间（2024-02：201 · 2024-03：1,942 · 2024-04：5 · 2024-09：1），468 个只有 `HH:MM`、没有日期，255 个没有表单。数据几乎全部集中在 2024 年 3 月。
- **发送时间**：只能从后续邮件的引用引导行中读出，精确到分钟。只有引导行能确定发送方（有客服发件人名称或其他发件人名称）、并且引用内容恰好与之前的一封邮件吻合时才采用，共恢复 258 封邮件的发送时间（`Message.sent_at`）。其余邮件的发送时间未知。

## 切分（train / dev / test）

`uv run copilot split --stats` 的结果（方法与理由见 [D-012](decisions.md)）：

| | train | dev | test |
|---|---|---|---|
| 线程 | 2,026（70.5%） | 432（15.0%） | 414（14.4%） |
| 客服回复：强 / 辅助 / 弱证据 | 1,281 / 328 / 316 | 303 / 56 / 66 | 271 / 64 / 74 |
| 案件状态：replied / open / undetermined | 911 / 403 / 712 | 207 / 86 / 139 | 185 / 78 / 151 |
| 重复提交的线程（380 组、773 个线程） | 560（72%） | 118（15%） | 95（12%） |

三侧在线程顺序的 10 等分中各段的线程数都接近均匀（test 每段 38–45 个），类别比例与整体一致。重复提交整组分配，并且按单位的起点分配（`_allocate`），所以多个线程一组的单位分到各侧的比例与单个线程相同；最初按“最欠缺的一侧”分配时，93% 的重复提交线程分到了 train（已修复，种子改为 `d012-v2`）。

选择切分方式时用到的观察：

- **线程 ID 就是提交顺序。** 按 ID 每 200 个线程分段，问题发生时间的中位数单调递增（ID 200–399 约为 2 月 28 日，1800–1999 约为 3 月 15 日，3000 以上约为 3 月 30 日）。问题发生时间是玩家填写的，有明显离群值（4 月、9 月），723 个线程没有完整日期。
- **从问题发生到客服回复**（有发送时间的 166 封）：中位数 8.8 小时，p95 约 5 天。
- **两次集中的事故**：问题发生时间为 3 月 2 日的线程有 340 个，3 月 15 日有 220 个，其他日子通常为 30–80 个。按时间先后切分时，这两次事故都只在 train 中，test 只代表月底。
- 按时间先后切分（`--method chronological`）时，test 的客服回复中有强证据的只占一半（163 / 323），而均匀切分时约三分之二（271 / 409）：越晚的回复越少被后续邮件引用佐证。

## 模板候选（train）

`uv run copilot kb build` 的结果。只用 train 的 2,026 个线程（D-012），跨线程的角色证据只在 train 内重新计算；方法见 [`backend/copilot/kb/`](../backend/copilot/kb/)。

- **只在 train 内计算证据后**，train 的 1,925 封客服回复中：强证据 1,257 封、只有“重复出现” 325 封、只有弱证据 343 封（不参与学习）。用全部线程计算时强证据是 1,281 封：差额来自信任只来自 dev 或 test 线程的回复。
- **82 个候选**：48 个有强证据，34 个只有“重复出现”（所有者批准前只在审核清单中）。另有 43 封回复所在的簇只出现在一个线程中，不成为模板。
- **覆盖率**（占 train 全部 1,925 封客服回复）：候选的来源回复占 79.9%，加上与候选近似（3-gram Jaccard ≥0.9）的弱证据回复占 82.1%。只算角色可信的回复（强证据和“重复出现”，1,582 封）时，来源回复占 97.3%。前 10、25、50 个候选分别累计覆盖 55.6%、65.7%、74.6%。覆盖率不设门槛，如实报告（[D-013](decisions.md)）。
- **措辞几乎固定**：82 个候选中只有 16 个簇内有不同的正文，差别都是多一句或少一句，没有一个是同一位置填了不同的值，所以自动识别的槽位为 0。7 个候选的正文中有固定的日期、时刻或时间窗口（大多是事故的时间），留给标注判断是否限定事故期间。
- 切分修复后重新构建时，63 个候选沿用了原来的 ID（61 个正文相同，2 个按来源回复重合），19 个是新的，13 个消失，没有歧义。

## 模板标注（train）

`uv run copilot kb annotate` 的结果（模型见 `.env` 的 `LLM_MODEL_ANNOTATE`，开发时用的是 OpenRouter 上的 `google/gemini-4-carbon`，flex 服务等级）。全部是未审核的初稿：

- **82 个候选全部标注成功**，没有失败；3 个（覆盖率排在 61 名之后）落到 `other`。模板最多的意图：`gameplay_question` 11、`bug_request_details` 10、`event_reward_question` 6、`birthday_input_issue` 6。按覆盖率最高的意图：`bug_investigating` 14.9%、`purchase_not_reflected` 11.5%、`ad_reward_not_received` 9.0%、`item_in_backpack` 8.9%。
- **风险**：high 17、normal 43、low 22。代码把风险调回意图默认风险的次数为 0（模型给出的风险都不低于默认风险）。
- **通用与限时**：模型判为通用的 52 个，其中风险为 low 的 13 个，属于自动发送允许清单中意图的 7 个（审核后才可能允许自动发送）。限定事故或期间的 10 个，其中 4 个建议对应到 `knowledge/notices.yaml` 中的事件。
- **known_from**：48 个有已知发送时间作为上界，34 个退回 train 中最晚的已知发送时间（3 月 30 日），历史重放中会比实际晚出现。
- 有缓存时重新运行不调用 LLM，输出逐字节相同。

## 标准答案（全部切分）

`uv run copilot kb label` 的结果：#7 评测用的标注，模板只来自 train。

| | train | dev | test |
|---|---|---|---|
| 客服回复 | 1,925 | 425 | 408 |
| 强证据的回复对应到模板（主指标用） | 96.1%（1,231 / 1,281） | 91.7%（278 / 303） | 92.6%（251 / 271） |
| 只有“重复出现”的回复对应到模板 | 94.5% | 91.1% | 87.5% |
| 弱证据的回复对应到模板 | 12.7% | 13.6% | 12.3% |
| 解决信号：resolved / unresolved / unknown | 1,727 / 190 / 8 | 378 / 45 / 2 | 358 / 50 / 0 |
| 不回复：重复提交 / 系统邮件 | 150 / 90 | 32 / 21 | 24 / 21 |

- 强证据的回复几乎全部精确匹配（近似匹配只有 3 封），因为强证据大多来自“与有佐证的回复正文相同”。dev 和 test 中约 8% 的强证据回复对应不上 train 的模板：这是知识库没有覆盖到的答复，评测时检索的上限。
- 弱证据的回复大多是只出现一次的个别答复，对应到模板的只有约 13%，所以 D-012 把它们作为单独的切片报告，而不放进主指标。
- 解决信号是近似的：玩家的追问可能只是道谢。

## 关键发现

1. **回复高度模板化。** 去掉引用内容和固定的问候语、结尾后（`Message.core`），2,759 封客服回复有 618 种不同的正文，**最常见的 50 种覆盖 71%，最常见的 100 种覆盖 79%**；另有 467 封是只出现一次的回复。这就是题目所说的“小型知识库”：核心工作是给咨询分类并检索出正确的模板，再由 LLM 调整措辞。
2. **部分模板只适用于某次事故。** 例如：3/2 11:00–14:00 的 App Store 故障导致购买异常；3/15 排名奖励出现“構成エラー”错误；以及一个“仍在调查中”的广告奖励问题。这些模板只在特定时间窗口内有效，不能用于无关的问题。
3. **回复遵循固定结构：** 问候 → 致歉（视情况）→ 答复 → “如果问题仍未解决，请再次联系我们” → `今後とも『ぽちゃガチョ！』をよろしくお願いいたします。` → `※本メール内容の無断掲載、無断複製、転送はお控えください。` 中文客服最容易在这类语体上出错，因此起草的回复应遵循这一结构。导入时把问候语和结尾拆到 `Message.greeting`、`Message.closing`；10 封客服回复没有结尾。
4. **引用的历史邮件很杂乱。** 共有 2,108 封邮件带有引用，按引用起点的格式：`>` 行 1,861 · Gmail 引导行（`2024年3月29日(金) 16:32 … <>:`，有时带 `午前/午後`）197 · `Original Message`/`____` 等分隔线 26 · 其他语言或折行的引导行 15 · iPhone 引导行（`2024/03/29 12:18、… のメール:`，有时后面不带 `>`）7 · `On … wrote:` 1 · Outlook 邮件头块 1。客服回复也会在结尾之后用 `>` 引用玩家的表单。约 15 封玩家邮件（约 0.5%）把之前的邮件不加任何引用标记地粘贴在正文里，规则无法安全地识别，这部分保留在 `body` 中。
5. **部分字符丢失。** `・`、`①②③` 和一些项目符号被替换成了半角 `?`。导入步骤修复了 1,020 封邮件中的常见情况：已知短语（如 `ご意見?ご要望`）449 处、行首的项目符号 2,303 处、汉字/片假名之间的分隔符 154 处、丢失的孤立字符 8 处。没有上下文的 `?` 保持原样，原文在 `Message.raw_body`。
6. **脱敏留下了空缺，但并不彻底。** 表单中的账号 ID、玩家名和邮箱地址都是空的，发件人地址显示为 `<>`。但自由文本中仍可能出现个人信息，例如从其他渠道转来的咨询中带有电话号码，所以引用样本时仍要遵守 [data/README.md](../data/README.md) 的规则。
